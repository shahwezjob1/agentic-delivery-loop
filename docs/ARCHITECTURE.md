# Root Repository Architecture

## 1. Purpose and scope

This document is the low-level design for code and configuration owned at the root of the `agentic-delivery-loop` monorepo. It defines repository-wide structure, dependency ownership, shared contracts, development orchestration, Cloudflare naming, type generation, provisioning, deployment, validation, and documentation rules.

It does not define the internal implementation of any application module. Each module owns a separate `docs/ARCHITECTURE.md` and `docs/REPO_MAP.md` below its application directory. Root documentation may state a module's public responsibility, deployment identity, bindings, and cross-module dependencies, but must not duplicate its internal classes, routes, database queries, prompts, tools, components, or workflow steps.

## 2. Architectural objectives

The root repository must make the following outcomes straightforward for a coding agent and for a human operator:

1. Install all exact dependencies with one package-manager command.
2. Typecheck, format-check, generate Cloudflare types, provision, migrate, run locally, and deploy from root scripts.
3. Deploy the five Cloudflare Workers independently while preserving a valid dependency order for first deployment.
4. Keep the UI Worker as the only public origin.
5. Keep cross-module data contracts in one dependency-light shared package.
6. Derive Service Binding RPC types from the target Worker implementation instead of maintaining handwritten duplicate service interfaces.
7. Run the complete application locally with one command when local execution is needed.
8. Prevent root configuration from absorbing module-specific business logic.

## 5. Public boundary and communication model

### 5.1 Only one public origin

`agentic-delivery-loop-ui` is the only Worker exposed through `workers.dev` or a future custom route. Every backend Worker must set `workers_dev: false` and must not declare a public route or custom domain.

This is a deployment invariant, not just a UI convention. A browser must never call Domain API, Wingman Agent, PO Workflow, or Dev Agent through a backend URL.

### 5.2 Browser-facing traffic

The UI Worker owns the browser-facing protocol surface:

- Static HTML, JavaScript, CSS, and other Vite assets.
- Same-origin Hono HTTP endpoints used by domain screens.
- Wingman WebSocket/HTTP agent routes.
- Dev Agent WebSocket/HTTP agent routes.
- Browser-bound error normalization and HTTP status mapping.

The UI gateway must not implement domain rules, agent tools, prompts, model selection, workflow decisions, persistence, or GitHub behavior.

### 5.3 Typed RPC for application operations

Domain operations use Cloudflare Service Binding RPC. The Domain API Worker exposes a `WorkerEntrypoint` class with public methods. Callers receive typed Service stubs generated by Wrangler.

Required Service Binding RPC directions are:

```text
UI Worker ---------> Domain API Worker
Wingman Worker ----> Domain API Worker
PO Workflow -------> Domain API Worker
Dev Agent Worker --> Domain API Worker
```

Every Domain API method returns `Promise<RpcResult<T>>` from `@agentic-delivery-loop/contracts`. Consumers do not rely on cross-Worker exception prototypes or `instanceof`; each consumer has one small `unwrapRpcResult()` helper that returns `data` or throws a module-local `DomainRpcError` carrying `code` and `message`. The UI gateway maps a failure result to its browser error DTO instead of throwing.

### 5.3.1 Dev-to-Wingman programmatic invocation

Dev Agent calls Wingman through a cross-Worker Durable Object namespace binding, not through a Service Binding and not by emulating the browser chat transport:

```text
Dev Agent Worker
  -> WINGMAN_AGENT (cross-Worker Durable Object namespace)
  -> getAgentByName(env.WINGMAN_AGENT, crypto.randomUUID())
  -> WingmanAgent.invokeTurn({ prompt })
  -> same internal Wingman turn executor used by browser chat
  -> { responseMessage, toolCalls }
```

`invokeTurn()` is a generic programmatic turn. Wingman uses its normal prompt, model, tool registry, and real tools and knows nothing about verification or the expected tool name. Dev compares `toolCalls[].toolName` with the expected tool name itself.

No browser can invoke these methods directly because the Service Binding and Durable Object capabilities exist only in the caller Worker's environment.

### 5.4 Fetch forwarding for agent streams

Browser chat traffic uses Service Binding `fetch()` forwarding rather than an RPC method:

```text
Browser WebSocket/HTTP
  -> UI Hono route
  -> WINGMAN_AGENT.fetch(forwardedRequest)
  -> Wingman routing and Durable Object

Browser WebSocket/HTTP
  -> UI Hono route
  -> DEV_AGENT.fetch(forwardedRequest)
  -> Dev Agent routing and Durable Object
```

The gateway preserves method, upgrade headers, body, query string, conversation identifier, and streaming `Response`. It must not consume or reconstruct a WebSocket response body. The target URL/path may be rewritten only as required by the module's documented routing contract.

### 5.5 Binding matrix

The following names are repository-wide contracts and must be used consistently in Wrangler configuration, generated types, and source code:

| Caller             | Binding         | Type                                                    | Target or resource                                      |
| ------------------ | --------------- | ------------------------------------------------------- | ------------------------------------------------------- |
| UI Worker          | `DOMAIN_API`    | Service Binding (RPC)                                   | `agentic-delivery-loop-domain-api`                      |
| UI Worker          | `WINGMAN_AGENT` | Service Binding (`Fetcher`, fetch/WebSocket forwarding) | `agentic-delivery-loop-wingman-agent`                   |
| UI Worker          | `DEV_AGENT`     | Service Binding (`Fetcher`, fetch/WebSocket forwarding) | `agentic-delivery-loop-dev-agent`                       |
| Wingman Worker     | `DOMAIN_API`    | Service Binding (RPC)                                   | `agentic-delivery-loop-domain-api`                      |
| Wingman Worker     | `WINGMAN_AGENT` | Local Durable Object namespace                          | `WingmanAgent` class in this Worker                     |
| PO Workflow Worker | `DOMAIN_API`    | Service Binding (RPC)                                   | `agentic-delivery-loop-domain-api`                      |
| Dev Agent Worker   | `DOMAIN_API`    | Service Binding (RPC)                                   | `agentic-delivery-loop-domain-api`                      |
| Dev Agent Worker   | `WINGMAN_AGENT` | Cross-Worker Durable Object namespace                   | `WingmanAgent` in `agentic-delivery-loop-wingman-agent` |
| Domain API Worker  | `DB`            | D1                                                      | D1 database `adl-sql-db`                                |
| PO Workflow Worker | `AI`            | Workers AI                                              | Workers AI                                              |
| PO Workflow Worker | `TICKET_INDEX`  | Vectorize                                               | Vectorize index `adl-vector-db`                         |
| PO Workflow Worker | `PO_WORKFLOW`   | Workflow                                                | Workflow `adl-po-workflow`                              |
| Wingman Worker     | `AI`            | Workers AI                                              | Workers AI                                              |
| Dev Agent Worker   | `AI`            | Workers AI                                              | Workers AI                                              |

The same binding name `WINGMAN_AGENT` has a different type in different Workers. That is intentional: each Worker's generated `worker-configuration.d.ts` gives it the correct type.

Dev Agent's cross-Worker Durable Object binding is configured as:

```jsonc
{
  "durable_objects": {
    "bindings": [
      {
        "name": "WINGMAN_AGENT",
        "class_name": "WingmanAgent",
        "script_name": "agentic-delivery-loop-wingman-agent",
      },
    ],
  },
}
```

If a module-specific LLD defines a different binding name or type, the root contract wins and the module documentation must be corrected.

## 6. Cloudflare resource and configuration policy

### 6.1 Fixed names

```text
D1 database:      adl-sql-db
Vectorize index:  adl-vector-db
Workflow:         adl-po-workflow
```

Cloudflare-generated resource identifiers, such as a D1 database UUID or Vectorize identifier returned by provisioning, are copied into the owning module's `wrangler.jsonc`. IDs are configuration data, not shared TypeScript constants.

### 6.2 One environment

Only the top-level Wrangler configuration is used. No `env` blocks, `--env` flags, development environment, staging environment, or production environment are created for this POC.

Local execution uses the same top-level configuration with locally simulated bindings by default. Secrets for local execution use module-local `.dev.vars` files and are never committed.

### 6.3 Wrangler file format

Every Worker uses `wrangler.jsonc`. TOML is not used. Each file includes the Wrangler JSON schema reference and is the source of truth for that Worker's bindings and runtime configuration.

### 6.4 Compatibility date

All five Workers use the same pinned `compatibility_date` selected on the day the repository is first implemented. The date remains unchanged for this one-time POC unless a required Cloudflare API explicitly requires a newer date.

Compatibility flags are module-specific. `nodejs_compat` is added only where a dependency needs it. Any binding, compatibility date, compatibility flag, module rule, entrypoint export, or Durable Object binding change requires regeneration of the affected `worker-configuration.d.ts`.

### 6.5 Source maps

All Workers set `upload_source_maps: true` for useful deployed stack traces. Source maps must not contain committed secrets; code must read secrets only from bindings.

## 7. Shared package architecture

### 7.1 `@agentic-delivery-loop/contracts`

This package is the only general cross-module runtime package. It owns values that must be serialized across Worker, browser, RPC, or stored-event boundaries:

- Domain DTOs and status unions.
- Domain RPC method argument types and result payload types. Strict input validation schemas belong to Domain API.
- The `RpcResult<T>` envelope returned by every Domain API method.
- Page request and page-result contracts.
- Normalized error payload contracts. Error `code` is an open `string`, not a closed union.
- Agent activity event contracts shared with the UI.
- Wingman programmatic-turn contracts (`InvokeWingmanTurnInput`, `WingmanToolCall`, `WingmanTurnResult`) and the Dev `WingmanVerificationResult`.
- Dev Agent public lifecycle state visible to the UI.

`UIMessage` is referenced through a type-only `import type { UIMessage } from "ai"`. This is the only permitted AI SDK reference in contracts; it emits no runtime import.

It must not contain:

- Worker entrypoint classes.
- Service Binding interfaces duplicating entrypoint methods.
- Hono routes or middleware.
- D1 queries or migration logic.
- Agent prompts, tools, model IDs, or orchestration.
- GitHub clients.
- React hooks or components.
- Cloudflare binding declarations.
- Module-specific constants that do not cross a boundary.

The package uses explicit exports through `src/index.ts`. Consumers import from the package name, not via `../../packages/contracts/src/...` paths.

The package must remain usable in Workers and browser code. It therefore avoids Node-only APIs and avoids importing Cloudflare runtime globals.

### 7.2 `@agentic-delivery-loop/tsconfig`

This package contains JSON-only reusable TypeScript configuration:

- `base.json` for strict shared compiler behavior.
- `worker.json` for Cloudflare Worker workspaces.
- `react.json` for the UI workspace.

It has no compiled output and no runtime dependency.

### 7.3 Dependency direction

Allowed dependency directions are:

```text
apps/* --------------------> @agentic-delivery-loop/contracts
apps/* --------------------> @agentic-delivery-loop/tsconfig
@agentic-delivery-loop/contracts -> zod
```

Forbidden directions are:

- Any package importing an application workspace.
- One application importing another application's source files.
- Root scripts importing module-internal business implementation.
- Contracts importing React, Hono, Wrangler, Agents SDK, AI SDK runtime code, or database clients.

Cross-Worker execution always goes through a configured binding, never through a source-code import.

## 8. RPC type generation

### 8.1 Source of truth

The target Worker's exported `WorkerEntrypoint` class (or Durable Object class, for `WingmanAgent`) is the source of truth for its callable RPC methods. `packages/contracts` supplies method argument and return payload types, including `RpcResult<T>` and `PageResult<T>`, but does not repeat full service interfaces.

Module LLDs must not define hand-written service interfaces such as `DomainApi`, `DomainApiRpc`, or `DomainApiEntrypoint`. They may list which methods they call, but the generated binding type is authoritative.

### 8.2 Generated declarations

Each Worker commits its generated `worker-configuration.d.ts`. The file is produced by `wrangler types` and never manually edited.

A caller that invokes another Worker must generate types with all required Wrangler configuration files supplied. For example, UI type generation includes the UI, Domain API, Wingman, and Dev Agent configurations. Dev Agent type generation includes Dev Agent, Domain API, and Wingman configurations.

The root `cf:types` operation invokes module-owned `cf:types` scripts in dependency-safe order. Each module script knows its exact config list. The root script must not synthesize or patch generated declaration contents.

### 8.3 Validation

`pnpm cf:types:check` regenerates all declarations and fails when the working tree changes. It is a manual validation command for the coding agent and human operator. There is no hosted CI requirement.

## 9. Root package management

### 9.1 Package manager

- pnpm is mandatory.
- The root `package.json` pins `packageManager` to an exact pnpm version.
- `engines.node` declares the supported Node.js major range.
- `pnpm-lock.yaml` is committed.
- npm, Yarn, and Bun lockfiles are ignored and must not be added.
- Workspace dependencies use `workspace:*`.
- Direct dependencies are declared in the workspace that imports them rather than being placed at root for convenience.

### 9.2 Root package

The root package is private and has no runtime entrypoint. Its dependencies are repository tooling only, such as TypeScript, Prettier, Wrangler, and any small cross-platform script dependency that is genuinely required.

Exact dependency versions come from the dependency baseline in section 9.3.

### 9.3 Dependency baseline

Root implementation begins with one dependency compatibility spike. The coding agent selects and installs exact versions once, verifies the required Agents SDK, AI SDK, Wrangler, Workflow, and Vite APIs, records them in workspace manifests and root `pnpm.overrides`, and commits the generated lockfile. Module implementations must use that baseline and must not independently select versions.

Packages covered by the baseline include at least:

```text
agents
@cloudflare/ai-chat
ai
zod
wrangler
vite
@cloudflare/vite-plugin
react
react-dom
hono
typescript
```

The compatibility spike is a minimal, throwaway verification performed before application logic is written. It must confirm:

1. `AIChatAgent` can stream a browser turn.
2. `useAgent` and `useAgentChat` connect to it.
3. `streamText()` supports the chosen Workers AI models.
4. Tool calls appear in the completed AI SDK result.
5. `getAgentByName()` can call `WingmanAgent.invokeTurn()` from another Worker.
6. `wrangler types` generates the Dev-to-Wingman cross-Worker Durable Object binding type.
7. The Cloudflare Vite plugin runs the UI with the four auxiliary Workers.
8. Workflow create, get-status, and restart APIs match the PO design.

Version policy:

- Exact versions only. No `^`, `~`, `latest`, or `*`.
- Root `package.json` carries `pnpm.overrides` for the verified versions of `agents`, `@cloudflare/ai-chat`, `ai`, `zod`, and `wrangler` so every workspace resolves one version.
- Versions are queried from the configured package registry, never assumed. The resolved versions are recorded in this section once the spike succeeds.
- Spike code is not committed as application source.

## 10. Root scripts and command semantics

Root scripts are the supported operator interface. They delegate to workspaces or root scripts and must work from repository root.

### 10.1 Quality commands

```text
pnpm typecheck       Recursively invoke each workspace typecheck script.
pnpm format          Run Prettier write across supported repository files.
pnpm format:check    Check formatting without modifying files.
pnpm cf:types        Generate Cloudflare types for all Workers.
pnpm cf:types:check  Regenerate types and fail if committed output changes.
pnpm validate        Run cf:types:check, typecheck,  format:check, and build.
```

There are no `test`, `test:unit`, `test:e2e`, Vitest, Playwright, test fixture, or coverage commands. Wrangler `--dry-run` is not used.

### 10.2 Build command and module script standard

```text
pnpm build
```

`build` delegates to workspaces that produce a build (the UI Worker).

Command terminology is fixed:

```text
dev     = run locally (never "deploy to local")
deploy  = deploy to Cloudflare
```

Every backend Worker workspace exposes exactly these scripts:

```json
{
  "scripts": {
    "dev": "wrangler dev",
    "typecheck": "tsc --noEmit",

    "cf:types": "wrangler types",
    "deploy": "wrangler deploy"
  }
}
```

The UI Worker workspace exposes:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "typecheck": "tsc --noEmit",

    "cf:types": "wrangler types",
    "deploy": "wrangler deploy"
  }
}
```

Domain API additionally exposes:

```json
{
  "scripts": {
    "db:migrate:local": "wrangler d1 migrations apply DB --local",
    "db:migrate:remote": "wrangler d1 migrations apply DB --remote"
  }
}
```

A module's `cf:types` script appends the extra `-c` configuration paths it needs for cross-Worker binding types (section 8.2).

### 10.3 Local command

```text
pnpm dev
```

The canonical local command starts the UI project with Vite and the Cloudflare Vite plugin. `apps/ui-worker/vite.config.ts` treats the UI as the primary Worker and supplies the other four Wrangler configurations as `auxiliaryWorkers`.

Consequences:

- One command starts the complete local application.
- Only the UI receives a browser-accessible local origin.
- Private modules remain reachable through local bindings.
- React HMR remains available.
- Local bindings are simulated unless explicitly configured otherwise.

A single backend Worker may also be run on its own with its workspace `dev` script (`wrangler dev`). Local execution is not deployment.

Local development is supported but is not the primary operating model. The README presents direct Cloudflare provisioning and deployment before local development instructions.

### 10.4 Provisioning commands

Root scripts provide idempotent or safely repeatable operator commands where the Cloudflare CLI permits:

```text
pnpm provision:d1
pnpm provision:vectorize
pnpm provision:verify
pnpm db:migrate:remote
pnpm db:migrate:local
```

`provision:d1` creates `adl-sql-db` only when absent and clearly reports the generated database identifier that must be written into the Domain API Wrangler configuration.

`provision:vectorize` creates `adl-vector-db` with 768 dimensions and cosine distance, matching the chosen embedding contract. It must not silently recreate an incompatible existing index.

The Workflow resource `adl-po-workflow` is declared and deployed from the PO Workflow module's Wrangler configuration rather than being represented by a separate root source module.

`provision:verify` checks that required account-level resources and expected Worker names exist and reports missing configuration without mutating resources.

### 10.5 Secret commands

The GitHub token is set only for the Dev Agent Worker:

```text
pnpm secret:github
```

The script delegates to the Dev Agent workspace and runs Wrangler secret input for the module-documented secret binding name. The root never reads, echoes, logs, writes, or stores the token.

Workers AI, D1, Vectorize, Workflow, Durable Object, and Service Binding access use Cloudflare bindings rather than user-managed API keys inside Worker code.

### 10.6 Deployment commands

```text
pnpm deploy:domain-api
pnpm deploy:wingman
pnpm deploy:po-workflow
pnpm deploy:dev-agent
pnpm deploy:ui
pnpm deploy:all
```

Each per-Worker command delegates to that workspace's deploy script. `deploy:all` is a fail-fast sequential script, not a parallel recursive deployment.

First-deployment order is:

1. `agentic-delivery-loop-domain-api`
2. `agentic-delivery-loop-wingman-agent`
3. `agentic-delivery-loop-po-workflow`
4. `agentic-delivery-loop-dev-agent`
5. `agentic-delivery-loop-ui`

Before first deployment, the operator provisions D1 and Vectorize, copies returned identifiers into the owning Wrangler files, applies remote D1 migrations, sets the Dev Agent GitHub secret, runs `pnpm validate`, and then runs `pnpm deploy:all`.

After initial deployment, a changed Worker is deployed independently. A caller is redeployed only when its own code or binding configuration changes. The POC does not use GitHub Actions, Cloudflare Builds, automated promotion, automatic rollback, or environment promotion.

## 11. UI build and static asset integration

The UI module owns its Vite and Cloudflare plugin configuration, but root architecture fixes these integration requirements:

- React and Worker code deploy as one UI Worker project.
- Vite builds browser assets and the Worker entrypoint.
- Static assets and Hono routes share the same origin.
- API and agent paths reach Worker code.
- Static asset requests are served through Cloudflare Workers Static Assets.
- Unknown non-API browser paths follow the UI module's SPA fallback policy.
- Asset routing must never convert an unknown `/api/*` or `/agents/*` request into `index.html`.

The UI module LLD must select the exact static asset routing options that satisfy these invariants.

## 12. formatting ownership

The no-test policy does not weaken production-source checks for unused imports, unsafe accidental `any`, unresolved promises, or React hook misuse.

### 12.1 Prettier

`prettier.config.js` is the sole formatting configuration. Formatting covers TypeScript, TSX, JavaScript, JSON, JSONC where supported, Markdown, YAML, and CSS. Generated files and lockfiles are excluded where formatting them would create noise or break generator ownership.

## 13. TypeScript policy

`packages/tsconfig/base.json` enables strict TypeScript behavior. At minimum, root policy requires:

- `strict: true`
- `noUncheckedIndexedAccess: true`
- `exactOptionalPropertyTypes: true`
- `noImplicitOverride: true`
- `noFallthroughCasesInSwitch: true`
- `useUnknownInCatchVariables: true`
- `forceConsistentCasingInFileNames: true`
- `skipLibCheck: true`
- `noEmit: true` for application typechecking

Module configs extend either `worker.json` or `react.json`. Root `tsconfig.json` is an editor/navigation solution file and does not force all applications through `tsc -b`. Root typechecking is script orchestration through pnpm.

## 14. Validation and manual smoke contract

Because this POC intentionally contains no automated test packages, the root `README.md` must define one deterministic manual smoke sequence after deployment:

1. Open the UI Worker public URL.
2. Confirm static assets and the shell load.
3. Open each read-only domain view and confirm gateway-to-Domain RPC succeeds.
4. Open Wingman and verify a supported calculation streams through the WebSocket gateway.
5. Submit an unsupported capability and verify the intended feature-request behavior.
6. Trigger or wait for the PO schedule and inspect PO logs.
7. Open Dev Agent and exercise the documented user-driven ticket flow only when a suitable ticket exists.

This smoke procedure references module-specific instructions instead of duplicating their detailed expected payloads.

## 15. Documentation authority and maintenance

The repository root contains only these active root LLD files:

```text
docs/ARCHITECTURE.md
docs/REPO_MAP.md
```

Maintenance rule:

- A root file, shared package, root script, dependency policy, deployment sequence, naming convention, cross-module binding, or root invariant change updates both root documents as applicable.
- A module-internal change updates that module's documents.
- A module change that modifies a binding, public gateway contract, shared DTO, workspace dependency, resource name, or deployment relationship also updates root documentation.

If root and module documents conflict on a repository-wide matter, root documentation wins. If they conflict on an internal module implementation, the module document wins unless it violates a root invariant.

## 16. Explicit root-level non-goals

The root implementation must not introduce:

- Authentication or authorization infrastructure.
- Multiple Wrangler environments.
- Public routes for backend Workers.
- API gateway products outside the UI Worker.
- Queues, rate limiting, service discovery, or load balancers.
- Turborepo, Nx, Changesets, Docker Compose, Terraform, Pulumi, or Kubernetes.
- GitHub Actions or automatic deployments.
- Automated tests, test runners, coverage tools, or fixture packages.
- A root database abstraction, root agent framework, or root business-logic package.
- Source imports between application workspaces.
- A second manually maintained representation of Worker RPC interfaces.
- Shared model IDs or prompt constants in `packages/contracts`.
- Automatic merge, deployment, rollback, or environment promotion.

## 17. Coding-agent acceptance criteria

Root-level implementation is complete only when all of the following are true:

1. The planned root tree exists and no module-internal code was moved to root.
2. `pnpm install --frozen-lockfile` succeeds from the repository root after the lockfile has been generated.
3. `pnpm cf:types`, `pnpm typecheck`, `pnpm format:check`, and `pnpm build` succeed.
4. The dependency compatibility spike passed and its exact versions are recorded in section 9.3, workspace manifests, root `pnpm.overrides`, and `pnpm-lock.yaml`.
5. `pnpm dev` starts one primary UI Worker and four auxiliary Workers with a single command.
6. Root scripts expose provisioning, migration, secret, per-Worker deployment, and ordered full deployment operations.
7. All shared imports use workspace package names.
8. All private Workers have `workers_dev: false`; only UI is public.
9. Binding names, Worker names, and resource names match this document exactly.
10. Generated `worker-configuration.d.ts` files are committed and reproducible.
11. `README.md` contains direct-cloud deployment, local run, validation, and smoke instructions.
12. No test framework, CI/CD configuration, alternate environment, or monorepo orchestrator has been added.
13. Root and module documentation links resolve and responsibilities are not duplicated.
