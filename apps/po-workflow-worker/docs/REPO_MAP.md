# PO Workflow Worker Repository Map

## 1. Purpose

This file inventories the PO Workflow Worker files, their responsibilities, and their major exports. It is the companion implementation LLD to `ARCHITECTURE.md`.

Assumed Worker root:

```text
apps/po-workflow-worker/
```

If the existing repository uses a different root, preserve the existing root and apply the relative structure below.

## 3. Root files

### `docs/ARCHITECTURE.md`

Contains the authoritative PO Workflow architecture, processing flow, invariants, boundaries, and forbidden behavior.

### `docs/REPO_MAP.md`

Contains this planned file inventory and export map.

### `package.json`

Responsibilities:

- define only dependencies required by this Worker;
- use the exact versions from the root dependency baseline (`docs/ARCHITECTURE.md` → Dependency baseline, root `pnpm.overrides`, committed `pnpm-lock.yaml`); module implementations must not independently select or change versions;
- use repository-standard scripts;
- avoid adding a test runner.

Expected scripts:

```json
{
  "scripts": {
    "dev": "wrangler dev",
    "typecheck": "tsc --noEmit",

    "cf:types": "wrangler types -c wrangler.jsonc -c ../domain-api-worker/wrangler.jsonc",
    "deploy": "wrangler deploy"
  }
}
```

`dev` runs the Worker locally. `deploy` deploys it to Cloudflare. `cf:types` supplies the Domain API config so the generated `DOMAIN_API` binding type includes its RPC methods.

### `worker-configuration.d.ts`

Generated by `cf:types` (`wrangler types`). Committed and never manually edited. Provides `Env`, including the `DOMAIN_API` Service Binding type.

Expected dependency categories:

- Cloudflare Workers types and Wrangler through the repository's established setup;
- `zod` for application-boundary validation;
- `@agentic-delivery-loop/contracts` (workspace) for Domain DTOs, inputs, `PageResult<T>`, and `RpcResult<T>`.

Do not add an agent framework, orchestration framework, queue library, or Vectorize wrapper library.

### `tsconfig.json`

Extends the repository-standard Worker TypeScript configuration. It must enable strict type checking and include `src/**/*.ts`.

### `wrangler.jsonc`

Required configuration:

- Worker name `agentic-delivery-loop-po-workflow`;
- `main: "src/index.ts"`;
- compatible date pinned by the implementation;
- Cron: `*/5 * * * *`;
- Workflow `adl-po-workflow` with binding `PO_WORKFLOW` referencing exported class `PoWorkflow`;
- Workers AI binding named `AI`;
- Vectorize binding named `TICKET_INDEX` for index `adl-vector-db`;
- Service Binding named `DOMAIN_API` targeting `agentic-delivery-loop-domain-api`;
- no public route configuration.

Conceptual shape:

## 4. Source files

### `src/env.ts`

Owns shared environment typing. It re-exports the Wrangler-generated `Env` from `worker-configuration.d.ts`, which contains:

- `PO_WORKFLOW`;
- `AI`;
- `TICKET_INDEX`;
- `DOMAIN_API`.

The `DOMAIN_API` type comes from `worker-configuration.d.ts` generated by `wrangler types` with the Domain API config supplied. Do not hand-write a Domain API service interface and do not import Domain API source code.

---

### `src/index.ts`

Responsibilities:

- export `PoWorkflow` for the Workflow binding;
- expose the scheduled handler as the Worker's default export;
- contain no PO orchestration logic;
- expose no public production `fetch()` handler.

Exports:

```ts
export { PoWorkflow } from './workflow/po-workflow';

declare const worker: ExportedHandler<Env>;
export default worker;
```

Expected default export behavior:

```ts
export default {
  scheduled(controller, env, ctx) {
    ctx.waitUntil(handleScheduled(controller, env));
  },
} satisfies ExportedHandler<Env>;
```

An optional local-only trigger is allowed only if the repository already has a safe convention that cannot become a deployed public route.

## 5. Scheduler

### `src/scheduler/singleton-policy.ts`

Owns all fixed-instance lifecycle policy.

Exports:

```ts
export const PO_WORKFLOW_INSTANCE_ID: 'po-singleton';

export type SingletonAction = 'create' | 'restart' | 'skip-active' | 'skip-unknown';

export function classifyWorkflowStatus(status: WorkflowInstanceStatus): SingletonAction;

export function isActiveWorkflowStatus(status: WorkflowInstanceStatus): boolean;
```

Required classifications:

- `queued`, `running`, `waiting`, `waitingForPause`, `paused` -> `skip-active`
- `complete`, `errored`, `terminated` -> `restart`
- unknown/unrecognized -> `skip-unknown`

Do not access Domain API, AI, or Vectorize from this file.

### `src/scheduler/scheduled-handler.ts`

Owns Cron-to-Workflow lifecycle control.

Exports:

```ts
export async function handleScheduled(controller: ScheduledController, env: Env): Promise<void>;
```

Responsibilities:

1. attempt to inspect `po-singleton`;
2. distinguish missing instance from other lookup errors using the pinned SDK behavior;
3. create it with `{ trigger: "cron" }` when absent;
4. skip active states;
5. restart terminal states;
6. system-log unknown states and lifecycle errors;
7. never create a second logical instance ID.

No request processing belongs here.

## 6. Workflow orchestration

### `src/workflow/workflow.types.ts`

Owns PO Workflow-specific serializable contracts.

Exports:

```ts
export interface PoWorkflowParams {
  trigger: 'cron';
}

export interface PoRunSummary {
  selected: number;
  created: number;
  linked: number;
  failed: number;
}

export interface EmbeddedRequest {
  requestId: string;
  embeddingText: string;
  embedding: number[];
}

export interface CandidateMatch {
  ticketId: string;
  similarityScore: number;
}

export interface HydratedTicketCandidate {
  ticketId: string;
  ticketName: string;
  ticketDescription: string;
  status: 'accepted' | 'in_progress' | 'done';
  similarityScore: number;
}

export interface CommitResult {
  action: 'create' | 'link';
  requestId: string;
  ticketId: string;
  ticketName: string;
  ticketDescription: string;
}

export type RequestProcessResult =
  | {
      outcome: 'created';
      requestId: string;
      ticketId: string;
    }
  | {
      outcome: 'linked';
      requestId: string;
      ticketId: string;
    }
  | {
      outcome: 'failed';
      requestId: string;
    };
```

All types returned from Workflow steps must be serializable.

### `src/workflow/workflow-options.ts`

Owns Workflow constants and step names.

Exports:

```ts
export const PENDING_REQUEST_PAGE_SIZE: 5;
export const ZERO_RETRY_STEP_CONFIG: WorkflowStepConfig;

export function buildStepName(input: {
  position: number;
  step: number;
  operation: string;
  requestId: string;
}): string;
```

`buildStepName()` must return:

```text
R{position}-S{step}-{operation}-{requestId}
```

Do not place model, threshold, or binding constants here.

### `src/workflow/po-workflow.ts`

Defines the Workflow entrypoint.

Exports:

```ts
export class PoWorkflow extends WorkflowEntrypoint<Env, PoWorkflowParams> {
  run(event: WorkflowEvent<PoWorkflowParams>, step: WorkflowStep): Promise<PoRunSummary>;
}
```

Responsibilities:

1. `step.do("load-pending-requests", ZERO_RETRY_STEP_CONFIG, ...)`;
2. call `loadPendingRequests()`, which calls `DOMAIN_API.listRequests({ page: 1, pageSize: 5, status: "pending" })` and returns `unwrapRpcResult(result).items`;
3. initialize summary;
4. sequentially iterate over returned requests with one-based positions;
5. call `processPendingRequest()` for each request;
6. update aggregate counts;
7. return summary;
8. write concise run-level system logs.

This file must not contain:

- prompt text;
- JSON Schema definitions;
- embedding extraction logic;
- Vectorize request construction;
- PO log message formatting;
- scheduler instance lifecycle logic.

### `src/workflow/process-request.ts`

Owns the exact Rn-S1 through Rn-S6 sequence.

Exports:

```ts
export async function processPendingRequest(input: {
  request: FeatureRequestDto;
  position: number;
  workflowInstanceId: string;
  step: WorkflowStep;
  env: Env;
}): Promise<RequestProcessResult>;
```

Required order:

```text
S1 normalize-and-embed
S2 query-vector-index
S3 load-candidates
S4 decide
S5 commit
S6 upsert-vector
```

Responsibilities:

- construct every step name through `buildStepName()`;
- set `currentStep` before each step for error logging;
- use `ZERO_RETRY_STEP_CONFIG` on every step;
- call specialized services rather than implementing their internals;
- wrap S1 through S6 in one request-level `try/catch`;
- call `logRequestFailure()` on failure;
- return `failed` without throwing after a per-request failure.

S6 is invoked for both actions. For a link result it returns a skip result without a Vectorize write.

```ts
export const EMBEDDING_MODEL = '@cf/baai/bge-base-en-v1.5' as const;

export const PO_MODEL_MAX_TOKENS = 900;
```

No environment-based model switching is required for the POC.

### `src/ai/embedding.service.ts`

Owns Workers AI embedding invocation and output extraction.

Exports:

```ts
export async function embedRequestText(input: {
  ai: Ai;
  requestId: string;
  text: string;
}): Promise<EmbeddedRequest>;

export function assertEmbedding(value: unknown): asserts value is number[];
```

Requirements:

- use `EMBEDDING_MODEL`;
- request `cls` pooling;
- extract one 768-dimensional embedding;
- require all values to be finite;
- return only serializable values;
- never log embeddings.

### `src/ai/po-prompt.ts`

Owns prompt construction only.

Exports:

```ts
export function buildPoDecisionMessages(input: {
  request: FeatureRequestDto;
  candidates: HydratedTicketCandidate[];
}): AiTextGenerationInput['messages'];
```

Prompt requirements:

- keep the system prompt as one readable multi-line template string (`SYSTEM_PROMPT`) so it can be edited by hand;
- cast the model as product owner and tech lead for Wingman who refines one request into one self-contained tool ticket (see ARCHITECTURE.md "Refinement policy");
- link only when the candidate fully delivers the request, otherwise create;
- allow one controlled generalization that still satisfies the original request;
- require a generic input analysis (valid domain, undefined values, growth in time/memory/precision, unusual values) whose results become explicit rules with concrete limits, rejecting rather than guessing, and extensible input shapes where free;
- require the description order Goal, Tool name, Inputs, Output, Rules, Examples, within 1,000 characters;
- require a one-sentence `refinementNote` for created tickets;
- include request name and description;
- include all surviving candidate fields and similarity scores;
- require create or link according to supplied schema;
- forbid linking outside supplied candidates;
- tell the model that score is advisory, not decisive;
- forbid reasoning output;
- specify 50-character ticket name maximum;
- specify 1,000-character description maximum.

Do not include raw embeddings.

### `src/ai/po-decision.service.ts`

Owns structured Workers AI inference.

Exports:

```ts
export async function decideCreateOrLink(input: {
  ai: Ai;
  request: FeatureRequestDto;
  candidates: HydratedTicketCandidate[];
}): Promise<PoDecision>;
```

Responsibilities:

- choose create-only schema when `candidates.length === 0`;
- otherwise use create-or-link schema;
- invoke `PO_DECISION_MODEL` with `stream: false`, `max_tokens: 900`, `temperature: 0.2`, and `response_format.type: "json_schema"`;
- decode the SDK response field;
- validate with Zod;
- trim generated create fields;
- call `assertSelectedCandidate()` for link;
- log one `po.decision` info event with request ID, action, candidate count and (for create) ticket name and `refinementNote`;
- make no retry or repair call;
- on any failure (call, decode, validation, candidate check) log `po.decision.fallback_create` with the root cause and return a create decision that copies the request name and description with `refinementNote: "Kept as requested."`.

Do not call Domain API or Vectorize here.

## 8. Policies and schemas

### `src/policies/text-normalizer.ts`

Exports:

```ts
export function normalizeWhitespace(value: string): string;

export function toEmbeddingText(request: Pick<FeatureRequestDto, 'name' | 'description'>): string;
```

`toEmbeddingText()` returns:

```text
{normalized name} {normalized description}
```

Use one space, no newline, no lowercasing, and no punctuation removal.

### `src/policies/candidate-policy.ts`

Exports:

```ts
export const VECTOR_TOP_K = 3;
export const MINIMUM_CANDIDATE_SIMILARITY = 0.7;

export function filterCandidateMatches(matches: CandidateMatch[]): CandidateMatch[];

export function assertSelectedCandidate(input: {
  ticketId: string;
  candidates: HydratedTicketCandidate[];
}): void;
```

Requirements:

- filter with `similarityScore >= 0.70`;
- preserve ranking;
- assert that a link ticket ID exactly matches one supplied candidate;
- do not calculate a second similarity value;
- do not introduce an environment-configured threshold.

### `src/policies/decision.schema.ts`

Owns both JSON Schema objects supplied to Workers AI and Zod schemas used at the application boundary.

Exports:

```ts
export const createDecisionZodSchema: z.ZodType<CreateDecision>;
export const poDecisionZodSchema: z.ZodType<PoDecision>;

export const createDecisionJsonSchema: Record<string, unknown>;
export const poDecisionJsonSchema: Record<string, unknown>;

export type CreateDecision = {
  action: 'create';
  ticketName: string;
  ticketDescription: string;
  refinementNote: string;
};

export type LinkDecision = {
  action: 'link';
  ticketId: string;
};

export type PoDecision = CreateDecision | LinkDecision;
```

Schema rules:

- discriminated by `action`;
- create requires only `action`, `ticketName`, `ticketDescription`, `refinementNote`;
- refinement note trimmed length 1 to 200 (shown in the PO log and Worker logs);
- link requires only `action`, `ticketId`;
- no additional properties;
- ticket name trimmed length 1 to 50;
- ticket description trimmed length 1 to 1,000;
- ticket ID non-empty.

The JSON Schema must use only structures supported by the selected model's `response_format` implementation. If the provider rejects a top-level `oneOf`, express an equivalent provider-compatible discriminated object without weakening application Zod validation.

## 9. Vectorize

### `src/vectorize/candidate-index.ts`

Owns Vectorize query and upsert calls.

Exports:

```ts
export async function queryCandidateMatches(input: {
  index: VectorizeIndex;
  embedding: number[];
}): Promise<CandidateMatch[]>;

export async function upsertCanonicalVector(input: {
  index: VectorizeIndex;
  ticketId: string;
  embedding: number[];
}): Promise<void>;
```

`queryCandidateMatches()`:

- asserts the input embedding;
- queries `topK: 3`;
- does not request values;
- does not require metadata;
- maps Vectorize record ID to `ticketId`;
- maps result score to `similarityScore`;
- applies `filterCandidateMatches()`.

`upsertCanonicalVector()`:

- upserts exactly one vector;
- sets `id` to ticket ID;
- stores the creating request embedding;
- writes no canonical request ID metadata;
- requires no metadata.

### `src/vectorize/canonical-vector.ts`

Owns pure vector-record construction.

Exports:

```ts
export function toCanonicalVector(input: {
  ticketId: string;
  embedding: number[];
}): VectorizeVector;
```

Requirements:

- assert 768 finite values;
- return `{ id: ticketId, values: embedding }` or the exact equivalent required by pinned Vectorize types;
- include no `canonicalRequestId`;
- include no redundant `ticketId` metadata.

## 10. Domain API adapter

### `src/domain/domain-rpc.ts`

Owns the single `RpcResult` unwrap helper. Domain DTOs, inputs, `PageResult<T>`, and `RpcResult<T>` are imported from `@agentic-delivery-loop/contracts`; this Worker does not redefine them.

Exports:

```ts
export class DomainRpcError extends Error {
  constructor(readonly code: string, message: string);
}

export function unwrapRpcResult<T>(result: RpcResult<T>): T;
```

`unwrapRpcResult()` throws `DomainRpcError(result.error.code, result.error.message)` when `result.ok` is `false` and otherwise returns `result.data`.

Do not define D1 schemas, transaction types, Domain API internal repositories, or a hand-written Domain API service interface here.

### `src/domain/domain-api.client.ts`

A thin typed adapter around the Service Binding. It keeps RPC naming and result unwrapping out of the Workflow orchestration. Each function calls `env.DOMAIN_API`, applies `unwrapRpcResult()`, and returns the direct business value.

Methods used (authoritative signatures come from the generated binding type): `listRequests`, `getTicket`, `createTicketAndLinkRequest`, `linkRequestToTicket`, `appendPoLog`, each returning `Promise<RpcResult<...>>`.

Exports:

```ts
export async function loadPendingRequests(input: {
  domainApi: Env['DOMAIN_API'];
}): Promise<FeatureRequestDto[]>;

export async function loadCandidateTickets(input: {
  domainApi: Env['DOMAIN_API'];
  matches: CandidateMatch[];
}): Promise<HydratedTicketCandidate[]>;

export async function commitPoDecision(input: {
  domainApi: Env['DOMAIN_API'];
  request: FeatureRequestDto;
  decision: PoDecision;
  candidates: HydratedTicketCandidate[];
}): Promise<CommitResult>;
```

Responsibilities:

- always request page 1, page size 5, status `"pending"`, and return `unwrapRpcResult(result).items`;
- perform no `getTicket()` calls when there are no matches;
- iterate over matches sequentially in Vectorize order;
- call `getTicket({ ticketId })` once per match, which results in at most three ticket RPC calls;
- preserve candidate ranking while hydrating tickets;
- associate each loaded ticket with its similarity score;
- construct trusted `requestId` inputs;
- call exactly one commit RPC;
- return the authoritative ticket returned by Domain API.

Do not implement Domain API validation or transaction logic.

## 11. Logging

### `src/logging/po-log.ts`

Owns the single persisted success-log format.

Exports:

```ts
export function formatSuccessfulPoLog(input: {
  request: FeatureRequestDto;
  commit: CommitResult;
}): string;

export async function appendSuccessfulPoLog(input: {
  domainApi: Env['DOMAIN_API'];
  request: FeatureRequestDto;
  commit: CommitResult;
}): Promise<void>;
```

`appendSuccessfulPoLog()` calls `appendPoLog({ message })` and applies `unwrapRpcResult()`. The message must be 1 to 3,000 trimmed characters (enforced by Domain API); with the 50-character name and 1,000-character description limits it always fits, so no truncation is performed.

Required text (three lines):

```text
Selected request ID: ... | Request name: ...
Created ticket ID: ... | Ticket name: ...
Refinement note: ...
```

or:

```text
Selected request ID: ... | Request name: ...
Linked ticket ID: ... | Ticket name: ...
Refinement note: Linked to existing ticket.
```

Append exactly one PO log after a successful S5 commit. Do not write PO logs for empty runs or failures.

### `src/logging/system-log.ts`

Owns concise structured console logging.

Exports:

```ts
export function logSchedulerInfo(event: string, context: Record<string, unknown>): void;

export function logSchedulerError(
  event: string,
  error: unknown,
  context?: Record<string, unknown>,
): void;

export function logRequestFailure(input: {
  workflowInstanceId: string;
  requestId: string;
  batchPosition: number;
  failedStep: string;
  error: unknown;
}): void;
```

Requirements:

- use `console.info` for concise lifecycle events;
- use `console.error` for failures;
- normalize unknown errors into name/message/optional stack;
- never log embeddings, prompts, raw model output, secrets, or chain-of-thought.

Allowed dependency direction:

```text
index
  -> scheduler
  -> workflow entrypoint export

scheduler
  -> singleton policy
  -> system logging

po-workflow
  -> process-request
  -> domain adapter
  -> workflow options/types
  -> system logging

process-request
  -> text normalizer
  -> embedding service
  -> candidate index
  -> domain adapter
  -> decision service
  -> PO logging
  -> system logging
  -> workflow options/types

po-decision.service
  -> prompt
  -> decision schemas
  -> candidate policy
  -> model constants

candidate-index
  -> candidate policy
  -> canonical-vector
```

Forbidden dependency directions:

- policies must not import Workflow orchestration;
- AI services must not call Domain API;
- Vectorize services must not call Domain API;
- scheduler must not process requests;
- Domain adapter must not invoke Workers AI or Vectorize;
- logging must not own business decisions.

## 13. Coding-agent completion criteria

Code generation is complete only when:

- every planned file is created or intentionally mapped to an existing equivalent;
- the Worker typechecks;
- `cf:types` regenerates `worker-configuration.d.ts` without changes;
- the Worker runs locally with `dev`;
- Workflow export and bindings resolve;
- no public route is introduced;
- all architecture invariants are represented in code;
- manual smoke instructions cover every scenario in `docs/ARCHITECTURE.md`;
- package versions come from the root dependency baseline and are not independently selected.

The coding agent must report any mismatch between these contracts and existing Domain API RPC names/types instead of silently inventing a second contract.
