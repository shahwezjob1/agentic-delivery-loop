# PO Workflow Worker Architecture

## 1. Purpose

The PO Workflow Worker is the scheduled product-owner automation for the Agentic Delivery Loop POC. It examines pending feature requests, compares each request with existing tickets using semantic search, and either:

- creates a new accepted ticket and links the request to it; or
- links the request to an existing ticket.

This document and `REPO_MAP.md` together are the implementation LLD for the PO Workflow Worker. If an older plan or PO-specific design statement conflicts with this document, this document wins.

## 2. Scope

### 2.1 In scope

- A Cloudflare Cron Trigger that runs every five minutes.
- A single reusable Cloudflare Workflow instance for PO processing.
- Loading at most five pending requests per run.
- Sequential processing of those requests.
- Durable per-request Workflow steps.
- Request embedding with Cloudflare Workers AI.
- Candidate retrieval from Cloudflare Vectorize.
- Candidate hydration through typed Domain API Service Binding RPC. Candidate hydration performs zero to three sequential `getTicket()` RPC calls.
- A structured create-or-link decision using Cloudflare Workers AI.
- Calling Domain API RPC to commit the decision.
- One canonical Vectorize record for each newly created ticket.
- One successful PO log per successfully processed request.
- Structured system logging for developer diagnostics.

### 2.2 Out of scope

- Public HTTP routes for the PO Workflow Worker.
- Browser access to the Worker.
- Authentication or authorization.
- A Durable Object lock.
- A request `processing` status.
- Request claim columns or per-request locks.
- Parallel request processing.
- One child Workflow instance per request.
- Queues.
- Distributed transactions between D1 and Vectorize.
- Idempotency keys or commit-result reconciliation.
- Automatic cleanup of stale Vectorize records.
- Internal implementation of Domain API operations.
- Unit, integration, component, or end-to-end test suites.

## 3. Cloudflare resources and bindings

The Worker requires these bindings:

```ts
interface Env {
  PO_WORKFLOW: Workflow<PoWorkflowParams>;
  AI: Ai;
  TICKET_INDEX: VectorizeIndex;
  DOMAIN_API: /* Wrangler-generated Domain API Service Binding type */;
}
```

`Env` is generated by `wrangler types` into `worker-configuration.d.ts`. The `DOMAIN_API` type comes from `worker-configuration.d.ts` generated by `wrangler types` with the Domain API config supplied. Do not hand-write a Domain API service interface and do not import Domain API source code.

Required infrastructure:

- Worker name: `agentic-delivery-loop-po-workflow`
- Cron Trigger: `*/5 * * * *`
- Workflow binding: `PO_WORKFLOW` (Workflow name `adl-po-workflow`)
- Workers AI binding: `AI`
- Vectorize binding: `TICKET_INDEX` (index `adl-vector-db`)
- Service Binding RPC: `DOMAIN_API` (service `agentic-delivery-loop-domain-api`)
- Vectorize index dimensions: `768`
- Vectorize distance metric: `cosine`

The Worker has no public route and does not implement a public `fetch()` API. Its default export contains the scheduled handler only. A local development trigger may exist only when explicitly guarded as development-only and must not be available in deployed production configuration.

## 4. Key design decisions

### 4.1 Singleton Workflow execution

Use one fixed Workflow instance ID:

```ts
const PO_WORKFLOW_INSTANCE_ID = 'po-singleton';
```

The Cron Trigger does not directly create a new Workflow instance on every invocation. The scheduled handler inspects the fixed instance and applies this policy:

| Observed condition               | Scheduler action                                |
| -------------------------------- | ----------------------------------------------- |
| Instance does not exist          | Create `po-singleton`                           |
| `queued`                         | Exit                                            |
| `running`                        | Exit                                            |
| `waiting`                        | Exit                                            |
| `waitingForPause`                | Exit                                            |
| `paused`                         | Exit; the POC assumes it will not remain paused |
| `complete`                       | Restart the same instance                       |
| `errored`                        | Restart the same instance                       |
| `terminated`                     | Restart the same instance                       |
| `unknown` or unrecognized status | Write a system error and exit                   |

The scheduler must not introduce a Durable Object, D1 lock, processing status, child Workflow, or new random instance ID.

The status inspection and create/restart operation must be contained in `scheduler/singleton-policy.ts` and `scheduler/scheduled-handler.ts`; do not spread lifecycle branching through `index.ts`.

### 4.2 Batch and ordering

Each Workflow execution loads page 1 of pending requests with:

```ts
const result = await env.DOMAIN_API.listRequests({
  page: 1,
  pageSize: 5,
  status: 'pending',
});
const requests = unwrapRpcResult(result).items;
```

The Domain API defines pending-request ordering as oldest first. The PO Workflow processes the returned array in that exact order and never processes more than five requests in one execution.

Processing is strictly sequential:

```text
R1-S1 ... R1-S6
R2-S1 ... R2-S6
...
R5-S1 ... R5-S6
```

The implementation must not use `Promise.all`, parallel loops, fan-out, or child Workflow instances.

### 4.3 Step retry policy

Every `step.do()` uses zero retries:

```ts
const ZERO_RETRY_STEP_CONFIG = {
  retries: {
    limit: 0,
    delay: '0 seconds',
    backoff: 'constant',
  },
} as const;
```

Use the exact SDK-compatible config shape supported by the pinned Cloudflare Workflow types. The semantic requirement is one initial attempt and no Workflow retry.

A request-level `try/catch` surrounds all six request steps. Failure of one request must not abort processing of later requests.

### 4.4 Unique step names

Step names must identify batch position, step number, operation, and request ID:

```ts
function buildStepName(input: {
  position: number;
  step: number;
  operation: string;
  requestId: string;
}): string;
```

Required format:

```text
R{position}-S{step}-{operation}-{requestId}
```

Examples:

```text
R1-S1-normalize-and-embed-req_123
R1-S2-query-vector-index-req_123
R1-S3-load-candidates-req_123
R1-S4-decide-req_123
R1-S5-commit-req_123
R1-S6-upsert-vector-req_123
```

The initial batch read is a separate durable step named:

```text
load-pending-requests
```

## 5. Workflow inputs and outputs

No request-specific input is needed when the singleton starts or restarts:

```ts
export interface PoWorkflowParams {
  trigger: 'cron';
}
```

The Workflow returns:

```ts
export interface PoRunSummary {
  selected: number;
  created: number;
  linked: number;
  failed: number;
}
```

Rules:

- `selected` is the number of pending requests returned by Domain API, maximum five.
- `created` increments after a successful create-and-link Domain RPC call.
- `linked` increments after a successful link Domain RPC call.
- `failed` increments once for each request whose processing throws.
- An empty batch returns all zeroes and produces no PO log.
- Per-request failures do not mark the Workflow execution errored.
- Failure of the initial `load-pending-requests` step is not caught by the per-request handler and may mark the Workflow execution errored.

## 6. Domain API RPC boundary

PO Workflow calls Domain API only through typed Service Binding RPC. It does not know or duplicate Domain API persistence logic.

All payload types (`FeatureRequestDto`, `TicketDto`, `PoLogDto`, `ListRequestsInput`, `GetTicketInput`, `CreateTicketAndLinkRequestInput`, `CreateTicketAndLinkRequestResult`, `LinkRequestToTicketInput`, `LinkRequestToTicketResult`, `AppendPoLogInput`, `PageResult<T>`, `RpcResult<T>`) are imported from `@agentic-delivery-loop/contracts`. PO Workflow does not redefine them.

For reference, imported from contracts:

```ts
interface PageResult<T> {
  items: T[];
  page: number;
  pageSize: number;
  totalPages: number;
}

type RpcResult<T> = { ok: true; data: T } | { ok: false; error: RpcError };
```

Methods used (authoritative signatures come from the generated binding type):

| Method                                                               | Return type                                            |
| -------------------------------------------------------------------- | ------------------------------------------------------ |
| `listRequests(input: ListRequestsInput)`                             | `Promise<RpcResult<PageResult<FeatureRequestDto>>>`    |
| `getTicket(input: GetTicketInput /* { ticketId } */)`                | `Promise<RpcResult<TicketDto>>`                        |
| `createTicketAndLinkRequest(input: CreateTicketAndLinkRequestInput)` | `Promise<RpcResult<CreateTicketAndLinkRequestResult>>` |
| `linkRequestToTicket(input: LinkRequestToTicketInput)`               | `Promise<RpcResult<LinkRequestToTicketResult>>`        |
| `appendPoLog(input: AppendPoLogInput /* { message } */)`             | `Promise<RpcResult<PoLogDto>>`                         |

The Domain adapter calls the binding, applies one `unwrapRpcResult()` helper, and returns direct business values to the Workflow:

```ts
export class DomainRpcError extends Error {
  constructor(
    readonly code: string,
    message: string,
  ) {
    super(message);
    this.name = 'DomainRpcError';
  }
}

export function unwrapRpcResult<T>(result: RpcResult<T>): T {
  if (!result.ok) throw new DomainRpcError(result.error.code, result.error.message);
  return result.data;
}
```

A thrown `DomainRpcError` is handled like any other per-request error (Section 8.1), or fails the `load-pending-requests` step.

The following are Domain API responsibilities and must not be implemented in PO Workflow:

- D1 transactions.
- ID generation.
- Creation of an accepted ticket.
- Request-to-ticket relationship persistence.
- Request status synchronization with ticket status.
- Validation of ticket existence and request state.
- PO log persistence.

## 7. Per-request pipeline

### 7.1 S1: Normalize and generate embedding

Normalize each field independently:

```ts
function normalizeWhitespace(value: string): string {
  return value.trim().replace(/\s+/g, ' ');
}

function toEmbeddingText(request: FeatureRequestDto): string {
  return `${normalizeWhitespace(request.name)} ${normalizeWhitespace(request.description)}`;
}
```

Rules:

- Use exactly one ASCII space between name and description.
- Do not insert a newline.
- Preserve case.
- Preserve punctuation.
- Do not remove stop words.
- Do not include request ID, status, or timestamps.

Use this embedding model:

```text
@cf/baai/bge-base-en-v1.5
```

Use `cls` pooling for both inserted vectors and query vectors. Extract the embedding according to the pinned Workers AI response type and assert:

- the result is an array;
- it contains exactly 768 values;
- every value is a finite number.

S1 returns serializable data equivalent to:

```ts
interface EmbeddedRequest {
  requestId: string;
  embeddingText: string;
  embedding: number[];
}
```

Never log the embedding or full model response.

### 7.2 S2: Query Vectorize and apply threshold

Query `TICKET_INDEX` with:

```ts
{
  topK: 3,
  returnValues: false,
  returnMetadata: "none",
}
```

If the pinned Vectorize types use a different value for disabling metadata, use the SDK-supported equivalent. No metadata is required.

The Vectorize record ID is the ticket ID. Map each hit to:

```ts
interface CandidateMatch {
  ticketId: string;
  similarityScore: number;
}
```

Apply the fixed POC threshold:

```ts
const MINIMUM_CANDIDATE_SIMILARITY = 0.7;
```

Discard matches whose score is less than `0.70`. Preserve the Vectorize result order for surviving matches.

The LLD assumes Vectorize records are not stale. Do not add stale-record cleanup, defensive deletion, or reconciliation logic.

### 7.3 S3: Load candidate tickets

If S2 returns no matches, return an empty candidate array without calling Domain API.

Otherwise call `DOMAIN_API.getTicket({ ticketId })` sequentially once for every surviving candidate, preserving the Vectorize ranking. Because `topK` is 3, this results in at most three ticket RPC calls. Iterate over surviving candidate matches in Vectorize order and load each ticket by ID. Combine each returned ticket with its similarity score:

```ts
interface HydratedTicketCandidate {
  ticketId: string;
  ticketName: string;
  ticketDescription: string;
  status: 'accepted' | 'in_progress' | 'done';
  similarityScore: number;
}
```

Preserve the S2 ranking. Matching is allowed against accepted, in-progress, and done tickets.

The POC assumes every candidate ID resolves successfully. Do not add stale-vector cleanup machinery.

### 7.4 S4: Structured create-or-link decision

Use:

```text
@cf/meta/llama-3.3-70b-instruct-fp8-fast
```

Inference configuration:

```ts
{
  messages,
  stream: false,
  max_tokens: 900,
  temperature: 0.2,
  response_format: {
    type: "json_schema",
    json_schema: schema,
  },
}
```

The exact request shape must follow the pinned Workers AI TypeScript definitions. Do not switch to prompt-only JSON, tool calling, or a smaller model.

#### With one or more candidates

The output type is:

```ts
type PoDecision =
  | {
      action: 'create';
      ticketName: string;
      ticketDescription: string;
      refinementNote: string; // 1..200 chars, one sentence: what was changed versus the request
    }
  | {
      action: 'link';
      ticketId: string;
    };
```

The prompt must include, for each candidate:

- ticket ID;
- ticket name;
- ticket description;
- current status;
- similarity score.

The model may:

- link only to a ticket in the supplied candidate array; or
- create a new ticket even when candidates are present.

After structured generation, perform these application boundary checks:

- Parse the model response using the response contract of the pinned SDK.
- Validate the decoded object with Zod.
- Trim generated ticket fields before final validation.
- For `create`, require ticket name length `1..50` and description length `1..1000`.
- For `link`, require `ticketId` to equal one of the supplied candidate IDs.
- Lowercase `action` before parsing so `Create` or `LINK` is accepted. Schemas are not strict: extra fields are ignored.
- The Zod schemas are the single source of truth; the JSON Schema sent to Workers AI is generated from them (`z.toJSONSchema`).
- Do not repair malformed output and do not make a second inference call.
- **Fallback.** If the inference call, response decoding, validation, or the candidate check fails for any reason (for example the model links to a ticket ID that is not a candidate), do not fail the request. Log `po.decision.fallback_create` with the request ID, candidate IDs and the error root cause to Worker logs, then create a new ticket using the request's own name and description with `refinementNote: "Kept as requested."`. This is not a repair or retry; no second inference call is made.

#### With no candidates

Still call the model. Use a create-only JSON Schema so a link response is not valid:

```ts
interface CreateDecision {
  action: 'create';
  ticketName: string;
  ticketDescription: string;
  refinementNote: string;
}
```

The model acts as product owner and tech lead (see "Refinement policy"). It must preserve every requirement in the request and must not invent unrelated scope.

#### Refinement policy

The PO step represents the refinement between a raw user request and the coding task. It is one non-conversational model call, so it is deliberately conservative:

- **Link only on full coverage.** Link when the candidate, once built, fully delivers the request. Partial coverage or doubt means create. A wrong link silently drops a requirement, which is the costliest mistake, so create is the default.
- **Generalize in one controlled way.** When a more general tool fully includes the requested behaviour and is just as simple (for example "multiply a list of two or more numbers" for "multiply two numbers"), the ticket may ask for the general tool, and the original case must still work. Nothing unrelated is added and no requirement is dropped.
- **Developer-ready description.** The description follows a fixed order: Goal, Tool name (snake_case), Inputs (with allowed range or size), Output, Rules, Examples (one normal, one rejected or edge case). The Dev Agent reads this description as its work order and registers the tool under the suggested name.
- **Input analysis, generically.** The prompt tells the model to reason about each input's valid domain, where the operation is undefined, how large inputs or results can grow (time, memory, precision), and which unusual values need a decision, then to write each finding as an explicit rule: reject with a clear error or define the exact result, with limits stated as concrete numbers. No operation-specific cases are written into the prompt. Because the description is capped at 1,000 characters, the prompt asks for compact phrasing and to drop background before dropping a rule.
- **Self-contained tools.** Tickets describe one Wingman tool with no network, storage, or new dependencies, because that is all the Dev Agent can build. Larger asks are narrowed to the closest self-contained tool.
- **Auditable.** `refinementNote` states what changed versus the request ("Kept as requested." when nothing). It is logged to Worker logs with the action so wrong refinements can be spotted.
- **Backstop.** A bad ticket costs one pull request review. A human starts the Dev Agent and a human merges. There is no multi-turn clarification in this POC; if refinement quality proves weak, add a second critique pass before adding conversation.

#### Prompt prohibitions

The system prompt must instruct the model:

- return only the schema-constrained result;
- do not output reasoning or chain-of-thought;
- do not link to an ID outside the supplied candidates;
- do not treat similarity score as the sole decision criterion;
- prefer create when no candidate is semantically appropriate;
- keep the ticket name within 50 characters;
- keep the ticket description within 1,000 characters;
- keep every requirement from the request and describe only one self-contained tool;
- give a one-sentence `refinementNote` when creating.

Never log complete prompts, raw model output, or reasoning.

### 7.5 S5: Commit through Domain API

For a create decision, construct the trusted RPC input in PO Workflow:

```ts
const input: CreateTicketAndLinkRequestInput = {
  requestId: request.id,
  ticketName: decision.ticketName,
  ticketDescription: decision.ticketDescription,
};
```

For a link decision:

```ts
const input: LinkRequestToTicketInput = {
  requestId: request.id,
  ticketId: decision.ticketId,
};
```

The model never supplies `requestId`.

Call exactly one Domain API commit RPC. Do not inspect or duplicate its internal transaction behavior.

After a successful commit, append exactly one PO log through Domain API.

The log is three short lines:

```text
Selected request ID: {requestId} | Request name: {requestName}
Created ticket ID: {ticketId} | Ticket name: {ticketName}
Refinement note: {refinementNote}
```

or, when linking to an existing ticket:

```text
Selected request ID: {requestId} | Request name: {requestName}
Linked ticket ID: {ticketId} | Ticket name: {ticketName}
Refinement note: Linked to existing ticket.
```

Descriptions are not logged; they are visible on the Requests and Tickets screens. The model's `refinementNote` for a created ticket is the third line of the PO log and is also written to Worker logs (`po.decision`). A linked request logs "Linked to existing ticket."

The PO log message must be 1 to 3,000 trimmed characters; Domain API enforces this. The short format (two IDs, two names of at most 50 characters and a note of at most 200 characters) always fits, so PO Workflow does not truncate it.

The PO log is a single persisted record, even though its message is multiline. It contains no embedding, prompt, raw model response, stack trace, or similarity score.

S5 returns a serializable commit result containing at least:

```ts
interface CommitResult {
  action: 'create' | 'link';
  requestId: string;
  ticketId: string;
  ticketName: string;
  ticketDescription: string;
}
```

### 7.6 S6: Upsert canonical vector

S6 always exists as a named durable step to keep the per-request sequence stable.

- For `link`, S6 returns a skipped result and performs no Vectorize mutation.
- For `create`, S6 upserts exactly one vector.

Created vector:

```ts
{
  id: commitResult.ticketId,
  values: embeddedRequest.embedding,
}
```

Rules:

- Vector ID equals ticket ID.
- Vector values come from the creating request's normalized name and description.
- Store no `canonicalRequestId` metadata.
- No metadata is required.
- A later linked request does not update the vector.
- Do not embed the generated ticket text.

D1 remains authoritative. Vectorize is eventually consistent. Do not attempt a distributed transaction or rollback if Vectorize upsert fails after Domain API commit.

## 8. Error handling

### 8.1 Per-request errors

Any error in S1 through S6 is caught by the request-level `try/catch`. The handler:

1. increments `failed` once;
2. writes a structured system error with `console.error`;
3. does not append a failure PO log;
4. continues with the next request.

System log context must include:

```ts
{
  workflowInstanceId: string;
  requestId: string;
  batchPosition: number;
  failedStep: string;
  errorName: string;
  errorMessage: string;
  stack?: string;
}
```

System logs may include developer-oriented error details but must not include:

- secrets;
- embeddings;
- complete prompts;
- raw model output;
- chain-of-thought.

### 8.2 Empty batch

If no pending request exists:

- write no PO log;
- make no AI, Vectorize, or additional Domain API calls;
- return a zero-valued `PoRunSummary`;
- complete successfully.

### 8.3 Partial commit and idempotency limitation

This POC intentionally does not implement commit idempotency or reconciliation. There is a residual edge case where Domain API may commit but PO Workflow may not receive the response. Do not add a processing status, idempotency key, or compensating transaction unless the product design is explicitly changed later.

## 9. Prompt and schema ownership

- `ai/po-prompt.ts` owns system and user message construction.
- `policies/decision.schema.ts` owns JSON Schema and Zod schemas.
- `ai/po-decision.service.ts` owns the Workers AI invocation and response decoding.
- `policies/candidate-policy.ts` owns the `0.70` threshold and candidate-ID assertion.

Do not duplicate schema definitions inside the prompt or Workflow orchestration file. Derive JSON Schema and Zod contracts from one clearly documented source where practical, while ensuring the exact JSON Schema passed to Workers AI is compatible with the provider.

## 10. Observability

### 10.1 PO logs

Persist exactly one PO log for each successfully committed request. Do not persist:

- batch-start logs;
- empty-run logs;
- candidate-selection logs;
- separate decision logs;
- failure logs.

### 10.2 System logs

Use `console.info` sparingly for scheduler lifecycle and run summaries. Use `console.error` for scheduler failures, unknown statuses, batch-load failures, and per-request failures.

Suggested events:

```text
po.scheduler.instance-created
po.scheduler.instance-restarted
po.scheduler.active-instance-skipped
po.scheduler.unknown-status
po.run.started
po.run.completed
po.request.failed
```

Messages must be concise and accompanied by structured fields.

## 11. Security and privacy

- No public route.
- No secrets in source control.
- No secrets in PO logs or console logs.
- No embedding values in logs.
- No raw prompts or model responses in logs.
- No chain-of-thought request or logging.
- Only candidate IDs returned by Vectorize and hydrated by Domain API may be sent as link options to the model.
- The model cannot choose the trusted request ID.
- Model output must pass schema validation and candidate-bound validation before Domain API invocation.

## 13. Required implementation invariants

The coding agent must preserve all of these invariants:

1. At most one `po-singleton` Workflow instance is active.
2. Cron runs every five minutes.
3. A run selects at most five oldest pending requests.
4. Requests are processed sequentially.
5. Each request has S1 through S6 durable steps.
6. Every step has Workflow retry limit zero.
7. One request failure does not abort later requests.
8. Embedding model and pooling are identical for insert and query.
9. Every embedding has exactly 768 finite numbers.
10. Vectorize uses cosine distance and top K of three.
11. Candidates below `0.70` are excluded.
12. The LLM receives similarity scores for surviving candidates.
13. The LLM may link only to a supplied candidate.
14. No-candidate inference uses a create-only schema.
15. Ticket name is 1 to 50 trimmed characters.
16. Ticket description is 1 to 1,000 trimmed characters.
17. PO Workflow supplies the trusted request ID.
18. Domain API owns persistence and transaction internals.
19. Only a newly created ticket gets a vector upsert.
20. Vector ID equals ticket ID and contains no canonical request ID metadata.
21. Exactly one PO log is written after each successful commit.
22. Empty runs and failed requests produce no PO log.
23. Developer error details go to system logs.
24. No public PO Workflow API is exposed.

## 14. Forbidden implementation choices

The coding agent must not introduce:

- a Durable Object singleton coordinator;
- a request `processing` status;
- request claiming;
- per-request Workflow instances;
- nested or child Workflows;
- parallel batch processing;
- Cloudflare Queues;
- a public `fetch()` endpoint;
- model-selected request IDs;
- prompt-only JSON parsing;
- a second model attempt on invalid output;
- automatic stale-vector deletion;
- canonical request ID metadata;
- vector updates when linking duplicates;
- distributed transaction emulation;
- new tests or test frameworks unless scope is separately changed.

## 15. Manual validation checklist

Because automated tests are out of scope, implementation is accepted through typecheck, `cf:types`, local run, and manual smoke validation.

Required scenarios:

1. Cron creates `po-singleton` when absent.
2. Cron skips an active `po-singleton`.
3. Cron restarts a completed instance.
4. Empty pending page completes with zero summary and no PO log.
5. One request with no threshold-qualified candidates creates a ticket.
6. One request links to a supplied candidate.
7. Model chooses create despite candidates being present.
8. A candidate below `0.70` is not sent to the model.
9. Invalid model output is rejected and the next request proceeds.
10. A Domain RPC failure is system-logged and the next request proceeds.
11. A successful create writes one PO log and one vector.
12. A successful link writes one PO log and no vector.
13. A Vectorize upsert failure is system-logged and later requests proceed.
14. Five requests produce sequential R1 through R5 steps.
15. No PO Worker public route is deployed.
