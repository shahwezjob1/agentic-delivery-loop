# Wingman Agent Worker Architecture

## 1. Purpose

The Wingman Agent Worker is a private Cloudflare Worker that hosts a conversational `AIChatAgent` backed by a SQLite Durable Object.

Wingman is a general tool-using assistant. Its initial capability set is deliberately small:

- perform addition through the registered `add` tool;
- discuss unsupported capabilities with the user;
- create a detailed feature request through the registered `create_feature_request` tool after conversational confirmation.

Addition is an initial capability, not the identity or permanent product boundary of Wingman. Future coding agents extend Wingman by adding tool files under `src/tools/` and registering them in `src/tools/tool-registry.ts`.

This document defines the Wingman Worker in detail and defines only the external contracts required from the UI Worker, Domain API Worker, and Dev Agent Worker. PO Workflow, ticket matching, Vectorize, and deployment automation are outside this document. The UI Worker stores the Wingman conversation ID in browser `localStorage` so a refresh reconnects to the same conversation; that storage is owned by the UI Worker.

## 2. Runtime and deployment boundary

`WingmanAgent` extends `AIChatAgent<Env>` from `@cloudflare/ai-chat`. Each conversation ID identifies one SQLite-backed Durable Object instance.

The Worker has no public route. It is reachable only through Cloudflare bindings:

- the UI Worker forwards browser chat traffic to the Wingman Worker through an ordinary Service Binding fetch (UI's `WINGMAN_AGENT` is a `Fetcher` Service Binding to `agentic-delivery-loop-wingman-agent`);
- the Dev Agent Worker reaches a fresh named `WingmanAgent` instance through a cross-Worker Durable Object namespace binding (Dev's `WINGMAN_AGENT` with `class_name: "WingmanAgent"` and `script_name: "agentic-delivery-loop-wingman-agent"`), not a Service Binding;
- Wingman calls the Domain API through a typed Service Binding.

Required bindings:

- `AI`: Workers AI binding;
- `DOMAIN_API`: Service Binding to the Domain API Worker (`agentic-delivery-loop-domain-api`); its type comes from `worker-configuration.d.ts` generated by `wrangler types` with the Domain API config supplied;
- `WINGMAN_AGENT`: Wingman's own local Durable Object namespace binding for `WingmanAgent`;
- `WINGMAN_AGENT` SQLite Durable Object migration, version `v1`.

The Worker must not expose a public hostname or route. It must not add public health, programmatic-turn, or domain endpoints.

## 3. External communication paths

### 3.1 Browser chat path

```text
Browser React chat
  -> same-origin UI Worker route
  -> UI Worker Service Binding fetch to Wingman Worker
  -> routeAgentRequest(request, env)
  -> WingmanAgent instance selected by conversation ID
  -> AIChatAgent chat protocol over WebSocket
```

The UI Worker is responsible for preserving the Agent route and WebSocket upgrade while forwarding. The canonical agent route is:

```text
/agents/wingman-agent/<conversationId>
```

The exact root prefix may be configured consistently by the UI and Wingman Workers, but the final forwarded request must remain compatible with `routeAgentRequest()`.

The browser must never call the Domain API or Wingman Worker directly.

### 3.2 Domain API path

```text
Wingman tool
  -> DOMAIN_API Service Binding RPC
  -> env.DOMAIN_API.createRequest(input): Promise<RpcResult<FeatureRequestDto>>
  -> unwrapRpcResult(result)
  -> D1 persistence owned by Domain API
```

Wingman does not access D1 directly and does not duplicate Domain API persistence logic.

### 3.3 Programmatic turn path (used by the Dev Agent)

```text
Dev Agent Worker
  -> generate fresh random conversation ID
  -> getAgentByName(env.WINGMAN_AGENT, conversationId)   // cross-Worker DO namespace binding
  -> call invokeTurn({ prompt })
  -> Wingman executes a real model-backed turn
  -> Wingman returns { responseMessage, toolCalls }
  -> Dev Agent compares toolCalls[].toolName with its own expected tool name
  -> Dev Agent discards conversation ID
```

`invokeTurn()` is a generic programmatic-turn adapter; Wingman knows nothing about verification. It is not a special model mode. Wingman is not told any expected tool name and does not determine pass or fail.

## 4. Conversation identity and persistence

Each conversation ID maps to exactly one `WingmanAgent` Durable Object instance.

The chat path must use the conversation ID supplied in the routed Agent URL. The programmatic path uses whatever named instance the caller selects; the Dev Agent generates a new, previously unused ID for every attempt.

The following concerns are separate:

1. **Persistence:** all user, assistant, and tool-related messages are retained in the SQLite-backed Agent conversation.
2. **Display:** the chat client can load and show the complete persisted conversation.
3. **Model context:** only approximately the most recent ten relevant complete messages are sent to the model on each turn.

Old messages must not be deleted merely because they are excluded from model context. Do not configure a ten-message persistence cap.

For the POC, conversations created through `invokeTurn()` are not explicitly deleted. The Dev Agent forgets the generated conversation ID after collecting the result, whatever its own decision.

## 5. Chat turn flow

`WingmanAgent.onChatMessage()` performs the standard interactive chat turn:

1. Read the messages already managed and persisted by `AIChatAgent`.
2. Validate the newest user text through `validatePrompt()`:
   - trim surrounding whitespace;
   - require 1 to 100 characters;
   - return a user-safe validation error for invalid input.
3. Convert persisted `UIMessage[]` into model messages using the supported AI SDK conversion abstraction.
4. Prune model input with the supported AI SDK pruning abstraction so that:
   - approximately the latest ten messages are retained;
   - recent conversation meaning is retained;
   - tool-call and tool-result relationships remain complete;
   - no orphaned tool result or incomplete tool exchange is sent;
   - persisted messages remain unchanged.
5. Build the Wingman system prompt using the registered tool names.
6. Create the complete tool object through `createWingmanTools(env)`.
7. Invoke `@cf/zai-org/glm-4.7-flash` through the Cloudflare AI SDK provider.
8. Permit a maximum of five model/tool steps for a turn.
9. Limit model output to approximately 400 output tokens per model call.
10. Keep parallel tool calls enabled.
11. Return the normal UI message stream response expected by `AIChatAgent` and `useAgentChat`.
12. Allow the Cloudflare chat harness to persist assistant and tool messages and to provide resumable streaming.

No custom WebSocket protocol, custom chat-message database, or alternate browser chat transport should be created.

## 6. Shared real-turn execution

Browser chat (`onChatMessage()`) and programmatic invocation (`invokeTurn()`) must use one shared turn definition so their behavior cannot drift.

`executeWingmanTurn({ modelMessages, systemPrompt, tools })` is the one internal executor responsible for model execution. It receives prepared model messages and execution options, then invokes the real model with the normal prompt and real registry tools.

```text
onChatMessage() -> executeWingmanTurn() -> streaming UI message response (browser)
invokeTurn()    -> executeWingmanTurn() -> await completion -> { responseMessage, toolCalls } (programmatic)
```

Conceptual contract:

```ts
interface ExecuteWingmanTurnInput {
  modelMessages: ModelMessage[];
  systemPrompt: string;
  tools: Record<string, Tool>;
}

// For reference, imported from @agentic-delivery-loop/contracts:
interface WingmanToolCall {
  toolCallId: string;
  toolName: string;
}

interface WingmanTurnResult {
  responseMessage: UIMessage;
  toolCalls: WingmanToolCall[];
}
```

The implementation may use the exact types exposed by `ai`, `@cloudflare/ai-chat`, `agents`, and `agents/models/ai-sdk` at the versions in the root dependency baseline. The coding agent must adapt the signatures to those APIs rather than inventing incompatible local replicas.

The shared execution service must own these invariants:

- model: `@cf/zai-org/glm-4.7-flash`;
- system prompt: `buildWingmanSystemPrompt()`;
- tools: `createWingmanTools(env)`;
- maximum five steps;
- approximately 400 output tokens per model call;
- parallel tool calls enabled;
- no unsupported operation may be answered through model calculation.

The browser adapter streams the turn. The programmatic-turn adapter waits for completion and returns the structured `WingmanTurnResult`. Both execute the same tools and prompt; there is no caller-specific prompt.

## 7. System prompt policy

`buildWingmanSystemPrompt(availableToolNames)` produces a concise prompt that establishes these rules:

### 7.1 Supported actions

- Use a registered tool when it can perform the requested action.
- Treat the registry provided for the current turn as the authoritative capability list.
- Do not claim a capability that is absent from the registry.
- Explain ordinary concepts and answer general conversational questions when no tool execution is required.

### 7.2 Unsupported operations

- Never calculate or simulate an unsupported operation using model reasoning.
- For example, if multiplication is not registered, do not answer `6 * 7`.
- Explain that the capability is unavailable.
- Discuss the desired feature and ask concise questions needed to understand it.

### 7.3 Feature-request discussion

Before calling `create_feature_request`, Wingman should understand enough to create an implementation-useful request. The discussion should identify, where relevant:

- requested behavior;
- expected input;
- expected output;
- one or more representative examples;
- important validation or error behavior;
- boundaries or exclusions explicitly stated by the user.

Wingman must generate:

- a concise request name no longer than 50 characters;
- a detailed description no longer than 1,000 characters.

The description should be self-contained so another coding agent can understand what to implement without reading the original chat.

### 7.4 Conversational confirmation

Wingman must obtain conversational confirmation before creating the request.

A separate redundant confirmation is not required when the user has already clearly instructed Wingman to raise or create the request and the required details are sufficiently clear. Otherwise, Wingman should summarize the proposed request and ask the user whether it should be created.

Vague discussion alone must not trigger request creation.

### 7.5 Duplicate behavior

Duplicate avoidance is prompt guidance only. Wingman does not search existing requests and the Domain API is not required by this LLD to reject duplicates.

## 8. Tool architecture

Every Wingman tool lives as an independent module under `src/tools/`.

`src/tools/tool-registry.ts` is the single explicit consolidation point for the Wingman tool set. The Agent imports and uses the consolidated object from this registry.

The registry is intentionally simple:

```ts
function createWingmanTools(env: Env): Record<string, Tool>;
```

It is not:

- a plugin loader;
- a metadata catalog;
- a dynamic file scanner;
- a shared input/output schema;
- a requirement for every tool to implement a custom common interface.

Each tool owns its individual Zod input schema, output shape, description, implementation, and validation.

Future coding agents adding a capability should normally:

1. add a new `*.tool.ts` file under `src/tools/`;
2. export its tool factory;
3. import and register it in `src/tools/tool-registry.ts`;
4. add or update any capability-specific types needed by that tool.

## 9. Initial tools

### 9.1 `add`

Factory:

```ts
createAddTool(): Tool<
  { left: number; right: number },
  { result: number }
>
```

Behavior:

- tool name: `add`;
- accepts exactly `left` and `right`;
- both values must be finite numbers;
- returns `{ result: left + right }`;
- contains no Domain API dependency;
- does not accept numeric strings;
- does not expose subtraction, multiplication, division, formula evaluation, or general expression evaluation.

### 9.2 `create_feature_request`

Factory:

```ts
createFeatureRequestTool(
  domainApi: Env["DOMAIN_API"] // generated Service Binding type
): Tool<
  { name: string; description: string },
  CreateFeatureRequestToolResult
>
```

Input policy:

- normalize whitespace by trimming and collapsing repeated whitespace;
- `name` must be nonempty and no longer than 50 characters;
- `description` must be nonempty and no longer than 1,000 characters;
- unknown input fields should be rejected by the schema;
- no duplicate lookup is performed.

Execution:

```ts
const request = unwrapRpcResult(
  await domainApi.createRequest({
    name: normalizedName,
    description: normalizedDescription,
  }),
); // throws DomainRpcError on { ok: false }, caught by the tool
```

Success result:

```ts
{
  ok: true;
  request: FeatureRequestDto;
}
```

Failure result:

```ts
{
  ok: false;
  error: string;
}
```

For this POC, the safe `DomainRpcError` message (from the Domain API `RpcError.message`) may be surfaced to the model in the tool result. Stack traces, Worker internals, binding details, SQL, and secrets must not be returned.

The tool must return a result for expected validation and Domain API failures rather than crashing the complete Agent turn.

## 10. Domain API contract required by Wingman

The `DOMAIN_API` binding type comes from `worker-configuration.d.ts` generated by `wrangler types` with the Domain API config supplied. Wingman does not hand-write a Domain API service interface.

Methods used (authoritative signatures come from the generated binding type):

| Method          | Input                                                                             | Returns                                 |
| --------------- | --------------------------------------------------------------------------------- | --------------------------------------- |
| `createRequest` | `CreateRequestInput` (`name` normalized 1..50, `description` normalized 1..1,000) | `Promise<RpcResult<FeatureRequestDto>>` |

`CreateRequestInput`, `FeatureRequestDto`, and `RpcResult<T>` are imported from `@agentic-delivery-loop/contracts`; Wingman does not redefine them.

Wingman has one small unwrap helper in `src/domain/domain-rpc.ts`:

```ts
export class DomainRpcError extends Error {
  constructor(
    readonly code: string,
    message: string,
  ) {
    super(message);
    this.name = 'DomainRpcError';
  }
}
export function unwrapRpcResult<T>(result: RpcResult<T>): T {
  if (!result.ok) throw new DomainRpcError(result.error.code, result.error.message);
  return result.data;
}
```

The Domain API remains the persistence and authoritative validation boundary. The request description limit is 1..1,000 trimmed characters in the shared contract, the Domain API input schema, and D1 (`CHECK (length(description) BETWEEN 1 AND 1000)`).

Wingman must not import Domain API implementation files.

## 11. Programmatic turn contract

### 11.1 Objective

`invokeTurn()` runs one real Wingman turn for a programmatic caller and returns a structured result instead of a browser stream. It is generic: Wingman knows nothing about verification.

The Dev Agent uses it to check that a natural-language prompt causes the actual Wingman Agent to invoke an expected registered tool. That check, and its limits (it does not prove wording, numeric correctness, edge cases, production safety, or UI rendering), belong to the Dev Agent.

### 11.2 RPC operation

The actual Agent instance exposes a public Durable Object RPC method:

```ts
// For reference, imported from @agentic-delivery-loop/contracts:
interface InvokeWingmanTurnInput {
  prompt: string; // same 1..100 trimmed rule as browser chat
}

interface WingmanToolCall {
  toolCallId: string;
  toolName: string;
}

interface WingmanTurnResult {
  responseMessage: UIMessage;
  toolCalls: WingmanToolCall[];
}

invokeTurn(input: InvokeWingmanTurnInput): Promise<WingmanTurnResult>;
```

The method accepts only `prompt`. Wingman never returns `passed`, `verified`, or any evaluation field.

### 11.3 Programmatic execution

A Dev Agent caller (Dev-owned; shown for context):

```ts
const conversationId = crypto.randomUUID();
const wingman = await getAgentByName(env.WINGMAN_AGENT, conversationId);
const result = await wingman.invokeTurn({ prompt: input.prompt });
const verified = result.toolCalls.some((call) => call.toolName === input.expectedToolName);
```

`env.WINGMAN_AGENT` in the Dev Agent is a cross-Worker Durable Object namespace binding. `expectedToolName` stays only in the Dev Agent and the comparison of `toolCalls[].toolName` is performed by the Dev Agent, not Wingman. The Dev Agent drops the conversation ID afterwards.

Within `invokeTurn()`, Wingman must:

1. apply the same user prompt length validation as browser chat;
2. persist the synthetic user message in the fresh Agent conversation using supported chat abstractions where possible;
3. build model messages from the persisted conversation;
4. call `executeWingmanTurn()` with the same pruning policy, prompt builder, registry, model, limits, and real tools as browser chat;
5. await completion instead of returning a browser stream;
6. persist the generated assistant and tool messages using supported `AIChatAgent` abstractions where possible;
7. return `{ responseMessage, toolCalls }`.

The implementation must prefer public, supported Cloudflare and AI SDK abstractions available at the baseline package versions. It must not depend on private package internals or manually write undocumented `AIChatAgent` SQLite tables.

If the baseline API cannot persist a programmatic turn through a supported abstraction, the coding agent should keep the real shared execution path and document the narrow persistence limitation for programmatic turns rather than duplicating the model/tool logic.

### 11.4 Time and failure behavior

- One `invokeTurn()` call performs one user turn.
- Use the same five-step model/tool ceiling as normal chat.
- A validation, model, or RPC failure rejects the `invokeTurn()` call; Wingman never reports pass or fail.
- The caller owns timeouts and result interpretation.
- No public HTTP endpoint is added for programmatic turns.
- The Dev Agent does not emulate the browser WebSocket/chat transport.

## 12. Error behavior

### 12.1 User input errors

Invalid browser input produces a concise user-safe response and must not invoke the model.

Invalid programmatic input causes `invokeTurn()` to reject with a typed or clearly classifiable input error.

### 12.2 Model errors

Model failures should be handled through the normal `AIChatAgent`/AI SDK error path. Do not expose bindings, secrets, stack traces, or internal prompts to the user.

### 12.3 Tool errors

- expected `create_feature_request` validation and Domain API errors become tool results visible to the model;
- unexpected exceptions are converted to a generic tool failure and logged server-side;
- one failed tool call must not fabricate a successful request;
- the model may explain the failure to the user based on the safe tool result.

## 13. Security and trust boundaries

- The browser is untrusted.
- User text is untrusted.
- Model-generated tool arguments are untrusted and must pass each tool's schema.
- Only tools returned by `createWingmanTools(env)` are executable.
- Wingman cannot dynamically execute scripts or arbitrary code.
- Wingman cannot access D1 directly.
- Wingman cannot inspect or mutate tools outside its deployed source.
- The Dev Agent cannot pass an expected tool name into Wingman's reasoning context; `invokeTurn()` accepts only `prompt`.
- Service bindings and Durable Object namespaces remain private Worker bindings.
- Secrets, stack traces, internal prompts, and raw Cloudflare errors must not be placed in user-visible text or tool results.

No authentication, rate limiting, request deduplication, production multi-tenant isolation, or abuse protection is added for this POC.

## 14. Observability

Use structured Worker logs for:

- conversation ID;
- execution path: `chat` or `programmatic`;
- turn outcome;
- invoked tool names;
- Domain API call success or failure;
- model or tool failure category;
- duration where easily available.

Do not log:

- secrets or bindings;
- full system prompts;
- full user conversations by default;
- raw stack traces in user-facing responses.

## 15. Package and type policy

Wingman depends on:

- `@agentic-delivery-loop/contracts` (workspace);
- `@cloudflare/ai-chat`;
- `agents`;
- `ai`;
- `zod`;
- Cloudflare Workers type packages used by the repository.

Uses the exact versions from the root dependency baseline (`docs/ARCHITECTURE.md` → Dependency baseline, root `pnpm.overrides`, committed `pnpm-lock.yaml`). Module implementations must not independently select or change versions.

Generate Worker and Service Binding types from the actual Wrangler configurations with `cf:types` (`wrangler types` with the Wingman and Domain API configs supplied). Use generated binding types instead of handwritten approximations.

Use the repository's existing package manager and lockfile. Do not create a second lockfile.

## 16. Wrangler configuration

The Wingman Worker Wrangler configuration must define:

- Worker name `agentic-delivery-loop-wingman-agent`;
- Worker entrypoint `src/index.ts`;
- Workers AI binding `AI`;
- Service Binding `DOMAIN_API` targeting `agentic-delivery-loop-domain-api`;
- Durable Object binding `WINGMAN_AGENT` mapped to `WingmanAgent`;
- SQLite Durable Object migration `v1` with `new_sqlite_classes = ["WingmanAgent"]`;
- no public routes.

Development environments may use local configuration supported by Wrangler, but production-like architecture remains private behind the UI Worker.

## 17. Entry-point behavior

`src/index.ts` must:

- export `WingmanAgent` so the Durable Object binding can resolve the class;
- call `routeAgentRequest(request, env)` for forwarded chat HTTP/WebSocket traffic;
- return `404` when the request is not an Agent route;
- not add a public REST API;
- export any Worker entrypoint required by the repository's typed Service Binding convention only if needed for private orchestration.

Programmatic callers target the named `WingmanAgent` Durable Object RPC method `invokeTurn()` directly (via a cross-Worker Durable Object namespace binding) rather than a second fake Agent class.

## 18. Non-goals and forbidden behavior

The Wingman Worker must not implement:

- subtraction in the initial registry;
- multiplication, division, formula evaluation, or generic expression evaluation;
- mental calculation of unsupported operations;
- feature-request duplicate search or prevention;
- deterministic approval state machines;
- a custom human-in-the-loop framework for request confirmation;
- PO Workflow logic;
- ticket creation or ticket matching;
- Vectorize access;
- GitHub integration;
- Dev Agent pass/fail decisions or any verification logic;
- browser conversation-ID storage (the UI Worker owns it, in `localStorage`);
- public Domain API or programmatic-turn routes;
- custom WebSocket chat protocol;
- a second message store;
- deletion of old messages when pruning LLM context;
- dynamic tool loading;
- a common custom schema shared by every tool;
- test suites or test packages for this POC.

## 19. Manual validation checklist

The implementation is ready for handoff when all of the following are demonstrated through typecheck, `cf:types`, local run, and manual smoke validation:

1. A browser can connect through the UI Worker and receive streamed Wingman responses.
2. Refresh/reconnect can show all messages for the same conversation ID.
3. A conversation longer than ten messages still displays old messages while model input is pruned.
4. `add` is invoked for a suitable addition request.
5. `6 * 7` is not calculated when no multiplication tool exists.
6. Wingman can discuss multiplication and prepare a detailed feature request.
7. Wingman does not create a request from vague discussion without conversational confirmation.
8. A direct instruction to create a sufficiently clear request does not require redundant confirmation.
9. Empty or oversized request name/description is rejected.
10. A valid description up to 1,000 characters reaches `DOMAIN_API.createRequest`.
11. A safe Domain API error is available to the model as a failed tool result.
12. An `invokeTurn({ prompt })` call on a fresh conversation ID returns `{ responseMessage, toolCalls }`.
13. Wingman never receives `expectedToolName`.
14. The Dev Agent can decide success by checking `toolCalls[].toolName`.
15. The Wingman Worker has no public route.

## 20. Decision summary

- Worker name and product terminology: Wingman Agent.
- Runtime: `AIChatAgent<Env>` with SQLite Durable Object persistence.
- Model: `@cf/zai-org/glm-4.7-flash`.
- Initial tools: `add`, `create_feature_request`.
- Registry: explicit consolidated object in `src/tools/tool-registry.ts`.
- Model context: approximately ten recent complete messages via supported pruning abstractions.
- Persistence/display: retain and show the complete stored conversation.
- Maximum steps: five.
- Approximate output cap: 400 tokens per model call.
- Parallel tool calls: enabled.
- Request name maximum: 50 characters.
- Request description maximum: 1,000 characters.
- Confirmation: conversational and prompt-guided.
- Duplicate handling: prompt guidance only; no lookup or deterministic prevention.
- Programmatic invocation: generic `invokeTurn()` Durable Object RPC returning `WingmanTurnResult`, sharing `executeWingmanTurn()` with browser chat; the Dev Agent (via cross-Worker DO namespace binding) evaluates tool calls.
- Domain API: `createRequest` returning `RpcResult<FeatureRequestDto>`, unwrapped by `unwrapRpcResult()`.
