# Domain API Worker Repository Map

## 1. Purpose

This file defines the planned file structure and major exports for `apps/domain-api-worker`. It must be implemented together with `docs/ARCHITECTURE.md`.

RPC envelope, DTO, input, result, status, and `PageResult<T>` types are owned by `@agentic-delivery-loop/contracts`. Files in this Worker import them; no file under `src/` defines or re-exports local copies.

## 2. Root files

### `package.json`

Responsibilities:

- define the Worker package name;
- depend on `@agentic-delivery-loop/contracts` for shared RPC and DTO types;
- expose repository-standard scripts.

Dependencies: uses the exact versions from the root dependency baseline (`docs/ARCHITECTURE.md` → Dependency baseline, root `pnpm.overrides`, committed `pnpm-lock.yaml`). Module implementations must not independently select or change versions.

Expected scripts:

```json
{
  "scripts": {
    "dev": "wrangler dev",
    "typecheck": "tsc --noEmit",

    "cf:types": "wrangler types",
    "deploy": "wrangler deploy",
    "db:migrate:local": "wrangler d1 migrations apply DB --local",
    "db:migrate:remote": "wrangler d1 migrations apply DB --remote"
  }
}
```

`dev` runs the Worker locally; `deploy` deploys it to Cloudflare. `cf:types` needs only this Worker's own config because the Domain API has no Service Bindings to other Workers. The manual smoke script is run directly against the local `dev` Worker; it has no package script.

Use the monorepo's selected package manager. Do not add a test runner.

### `tsconfig.json`

Responsibilities:

- extend the root TypeScript configuration when available;
- enable strict TypeScript;
- include `src`, `scripts`, and generated Worker types;
- emit no JavaScript during typecheck.

### `worker-configuration.d.ts`

Generated by Wrangler. It supplies Cloudflare runtime and binding types. Do not manually maintain contradictory binding definitions.

### `wrangler.jsonc`

Responsibilities:

- set the Worker `name` to `agentic-delivery-loop-domain-api`;
- set the Worker entrypoint to `src/index.ts`;
- bind D1 as `DB`;
- declare the D1 database `adl-sql-db` and the migrations directory;
- define no public routes or custom domains;
- use the shared pinned compatibility date from the root architecture;
- contain no Workers AI, Vectorize, Workflow, Durable Object, KV, R2, Queue, or secret binding.

## 3. Migration

### `migrations/0001_initial.sql`

Creates:

- `tickets`;
- `feature_requests` with nullable foreign key to `tickets`;
- `po_logs`;
- all status and length checks;
- all required indexes.

The migration must enable or respect foreign-key behavior supported by D1. Table creation order must allow the request foreign key to reference tickets.

Required indexes:

```sql
idx_feature_requests_status_created
idx_feature_requests_linked_ticket
idx_tickets_status_created
idx_po_logs_created
```

Once applied remotely, this file is immutable.

```ts
    ticket: TicketRow;

  completeTicketAndSynchronizeRequestsAtomic(input: {
    ticketId: string;
    timestamp: string;

```

Implementation requirements:

- all SQL remains in this file;
- `findOldestAccepted` orders by `created_at ASC, id ASC`;
- create/start/complete multi-table operations use D1 `batch()`;
- guarded status predicates are mandatory;
- all statements in one operation use the same timestamp;
- result metadata is checked strictly;
- rows are re-read after successful writes when needed to return authoritative state;
- no generic `patch`, `updateStatus`, transaction callback, or delete method.

`linkRequestToTicket` is a single guarded request update after the service has loaded both records. It copies the supplied current ticket status. It must require the request to still be pending and unlinked.

The service does not implement idempotency, relinking, duplicate-call recovery, verification evidence, AI decisions, or Vectorize behavior.

## 13. Manual smoke script

### `scripts/smoke-rpc.ts`

Purpose:

- provide repeatable manual local validation without adding a test framework;
- call the locally running Worker through the repository-approved Service Binding/local harness mechanism;
- print concise pass/fail results;
- exit non-zero on a failed check.

Scenarios:

1. create a request;
2. get and list it;
3. list with `status: pending`;
4. create a ticket and link the request;
5. create another request and link it to an existing ticket;
6. start the oldest accepted ticket;
7. confirm linked request synchronization;
8. save and replace a pull-request string;
9. complete a ticket;
10. confirm linked request completion;
11. append and list PO logs;
12. verify deterministic pagination;
13. verify normalized validation, not-found, conflict, and invalid-transition results.

Do not introduce Vitest, Jest, component tests, fixtures, or coverage tooling.

## 15. Coding-agent completion checklist

The implementation is complete only when:

- every planned file exists or an explicitly equivalent consolidation is documented;
- no local copies of contracts-owned RPC, DTO, input, status, or pagination types exist;
- no generic request or ticket patch RPC exists;
- no delete RPC exists;
- no public `fetch()` exists;
- D1 schema checks match all approved length and status rules;
- request/ticket list status filters are implemented;
- pagination defaults, clamps, `totalPages`, and ordering match this LLD, and public page results contain no `total`;
- create/start/complete multi-table writes are atomic D1 batches;
- all multi-row writes share one timestamp;
- guarded expected states and affected-row checks are present;
- link-to-existing copies accepted, in-progress, or done status;
- saving a pull-request value replaces the prior value and performs no URL validation;
- completion does not require a pull-request value;
- errors are normalized and serializable;
- typecheck, `cf:types`, local migration, local run, and manual smoke validation succeed;
- no AI, Agent, Workflow, Vectorize, GitHub, auth, rate-limit, queue, or automated-test code is added.
